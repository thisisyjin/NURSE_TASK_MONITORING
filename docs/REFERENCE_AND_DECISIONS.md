# 근거 자료, 확정 사항, 충돌 및 미확정 항목

Cursor가 제안서의 이상적인 운영 시스템을 그대로 만들거나, 이전 시연의 구 기준을 다시 복사하지 않도록 정리한 문서다. **자료에서 확인된 내용**과 **현재 개발 편의를 위한 선택**을 구분한다.

## 1. 원본 자료별 참고 범위

### A. 기존 HTML 시연판

- 사용자가 Cursor에 추가로 제공할 예정이다.
- 기존 레이아웃, 스타일, 간호사 카드, 계산 결과, 버튼, 09:00 이후 상태 전환을 파악하는 가장 직접적인 코드 자료.
- **이번 가이드 작성 환경에는 HTML 파일이 제공되지 않았다.** 따라서 실제 DOM 구조, 이벤트명, CSS, 데이터 배열, 실행 로직은 확인하지 못했다. Cursor는 HTML을 받아 먼저 분석해야 한다.
- HTML에 있는 모든 계산식이 최신 업무 기준이라고 간주하지 않는다.

### C. `[제안서]간호업무량기반 실시간 간호지원체계_20261030.pdf`

- p.1: 현장 문제, 목적, 업무 흐름과 필요성. 간호사별 성과 평가 목적이 아님.
- p.2: 기본 부하(KTAS, NEWS), 변동 부하(처방, 활력 등), 인력 적정성, 처방 적시성.
- p.3: 1~4단계 지원 방식, 지원 기록, 장기 AI 예측, 역할별 화면.
- p.4: 운영 원칙, 권한과 정보보안, 가상 데이터 사용.
- p.5: 원래의 3단계 추진 방향과 첨부 HTML 및 PDF 설명.

**주의:** 제안서는 장기 목표도 포함한다. 이번 React 1차에서 모든 제안 기능을 완성할 필요는 없다.

### E. `간호업무량_시연화면기준_가상데이터_입력표(1).xlsx`

- 시트: `데이터 입력` 하나.
- C열: 기존 시연 화면 예시 데이터.
- D열: 간호부의 추가 예시 또는 수정 요청값을 작성하도록 의도된 열. 현재 제공된 파일은 헤더가 `실제 예시 데이터 (기입)`으로 되어 있다. 최신 논의에서는 이를 `수정 요청값`의 역할로 사용할 예정이다.
- E열: 설명과 최신 협의에서 달라진 점.
- **D열이 비어 있으면 C열을 그대로 사용**한다. 빈칸을 삭제 요청으로 해석하지 않는다.
- 같은 행이라도 설명(E열)의 최신 변경 내용을 반드시 확인한다. 시연 숫자(C열)는 구 기준일 수 있다.

## 2. 현재 프로젝트에서 결정된 사항

| 주제 | 결정 | 근거 또는 이유 |
| --- | --- | --- |
| 개발 프레임워크 | **React 프론트엔드** | 사용자의 최근 개발 결정. 구 PDF의 HTML이라는 표현보다 우선 |
| 백엔드 | 별도 FastAPI 및 운영 DB 없음 | 시연용 프로토타입으로 충분 |
| Agent Builder | Langflow 기반 기존 연구실 서비스 활용 | Flow별 API를 추후 React에서 호출 |
| 초기 연동 방식 | Mock F1~F4 서비스 | Flow가 아직 준비되지 않아 UI를 먼저 완성 |
| 데이터 | HTML 및 엑셀에서 추출한 가상 JSON, 필요 시 localStorage | 실제 연동과 영속 DB가 필요 없는 1차 범위 |
| 주요 시연 | 간호사 업무량, 처방 대기 및 지연, 지원 요청과 추천 및 기록 | 기존 HTML과 시연 PDF, 간호부 답변 |
| 미래 예측 | 1차에서 제외 | 데이터 수집 및 검증이 필요한 2차 내용 |
| 간호사별 단계 | 여유, 보통, 높음 3단계 | 시연 화면 및 간호부 답변 |
| 인력 기준 | **담당 환자 수 × 50분** | 최신 간호부 답변 |
| 지원 결정 | 추천은 참고용, 책임간호사가 최종 결정 | 최신 간호부 답변 |
| 개인정보 | 합성 가상 데이터만 | 연구 목적과 의료정보 보호 |

## 3. 혼동하지 말아야 할 항목

### 3.1. 처방 수행시간과 대기시간

예: `정맥 항생제 10분, 대기 55/기준 30분`이라고 표시된다면 다음을 뜻한다.

- **10분:** 해당 처방의 예상 수행시간. 위쪽 `대기 처방 업무량`에 합산.
- **55분:** 처방이 발생한 뒤 아직 수행되지 않은 경과시간.
- **30분:** 수행 목표시간. 55분이 이를 초과했으므로 경고 표시.

아래쪽 수행시간을 모두 합하면 위쪽 대기 처방 시간이 된다는 점을 테스트한다.

### 3.2. 관찰 및 활력의 시간 산정

- 관찰: 환자 상태에 따른 관찰 예상시간.
- 활력: 활력징후 측정 예상시간.
- 최신 답변은 예상 소요시간의 정의와 향후 문헌 검토 방향을 설명하지만, **환자별 관찰시간을 KTAS 및 NEWS로 계산하는 구체적 식까지 확정한 것은 아니다.**
- 현재 구현은 원본 시연값을 사용하고, 근거 없는 계산식을 새로 만들지 않는다.

### 3.3. 50분이라는 숫자는 두 곳에 등장한다

1. 카드 업무량 단계에서 30분 및 50분은 **시연용 상태 구분값**이다.
2. 인력 적정성에서 **담당 환자당 50분**은 간호사별 또는 근무조별 예상 업무량과 비교하는 기준이다.

**두 기준은 별개이며 같은 값이라는 이유로 합치거나 관찰시간에 가산하지 않는다.**

### 3.4. 1시간 뒤 예상 업무량

- 원래 HTML과 PDF의 시연 규칙으로 계산된 표시값이며, 실제 학습된 예측 AI 결과가 아니다.
- 1차에서는 화면 유사도 때문에 유지할 수 있지만 `시연용 예상값`으로 명시하거나 후속 기능 영역으로 처리한다.

### 3.5. 지원 알림 10분 앞당김

- 우선 대상의 **지원 알림 시점만** 앞당긴다.
- 의료 처방의 원래 수행 마감시간과 F3 초과 판정 기준은 변경하지 않는다.

### 3.6. NEWS 상승 표시

- 이전 원시 점수 대비 증가라는 이유만으로 화살표를 표시하지 않는다.
- 간호부 답변: NEWS 위험 단계가 상승했을 때 화살표.
- 위험 단계: 양호 0~1, 주의 2~4, 위험 5~6, 고위험 7 이상.
- SpO2 미입력이 가상 시나리오에 있다면 `SpO2 미입력` 경고 표현을 검토한다. 실제 누락 데이터를 만들어 넣지는 않는다.

### 3.7. KTAS 상향

- 간호부 답변에서 KTAS가 상향되면 환자 악화의 예시로 제시되었다.
- 구현할 때 **KTAS 숫자가 커졌다는 뜻으로 해석하면 안 된다.** KTAS 1이 더 높은 응급도이므로, 최신 상태 악화 이벤트의 의미를 구분해야 한다.
- 가장 안전한 초기 시연 구현은 환자 악화 이벤트 플래그에 따라 `높음`을 표시하는 것이다.

## 4. 확인되지 않았으므로 임시값으로 관리할 항목

| 항목 | 현재 권장 방식 | 나중에 확인할 것 |
| --- | --- | --- |
| 관찰 소요시간 산정식 | 기존 관찰 시연값 사용 | KTAS, NEWS 또는 다른 간호요구도를 어떤 방식으로 반영하는지 |
| 활력 소요시간 산정식 | 기존 활력 시연값 사용 | 활력 주기 및 측정 1회 시간의 실제 기준 |
| 처방 분류 및 소요시간 | 기존 화면에 나온 처방만 시연 기준표 적용 | 간호부 검토를 거친 예상 소요시간 |
| 업무량 단계 구간 | 30분 및 50분을 `demoConfig`에 분리 | 실제 50분 경계와 추후 기준 보정 |
| 지원 단계의 지속시간 | 시연에 필요한 범위에서 명시적 데모 규칙 사용 | 높음 15~30분 등의 구체적인 운영 기준 |
| 지원자 추천 세부 우선순위 | 지원 가능 여부, 낮은 업무량 기준의 단순 Mock | 현장 적용 시 우선순위와 예외 |
| 역할별 기본 업무량 | 기존 HTML에 값이 있으면 그대로 재현 | Pre-T 등 역할에 대한 산정 기준 |
| 지원 배정 후 수락 시점 | 최신 답변의 수락 및 거절을 UI에서 재현 | 기존 HTML과 이벤트 순서 차이 |
| 일반 간호사 지원 알림 범위 | 본인 배정 알림과 관리자용 지원 알림 구분 | 역할별 상세 승인 정책 |

## 5. 자료 간 불일치가 있는 부분

1. **김서연 업무량:** 초기 엑셀 예시는 관찰 40, 활력 12, 대기 처방 83, 총 135분. 사용자가 후속 대화에서 보여준 별도 카드에는 관찰 45, 활력 15, 대기 처방 83, 총 143분. 두 예시를 혼합하지 않는다.
2. **기존 근무조 적정 인력:** 구 시연은 간호사 4명 × 50분 = 200분. 최신 답변은 환자 수 × 50분으로 수정. 09:00의 구 시연 `241분 > 200분` 알림을 최신 기준으로 그대로 유지할 수 없음.
3. **지원 배정 절차:** 구 PDF는 배정과 시작을 간단히 시연. 간호부는 알림, 확인, 수락, 거절과 사유 선택을 추가 요청. 새 UI에서는 과도한 분기 없이 이를 반영.
4. **NEWS ↑ 표시:** 구 화면의 표시가 최근 확정된 위험 단계 상승 규칙과 맞지 않을 수 있음. 동작 기준은 최신 답변 우선.
5. **시연 구현 기술:** 과거 협의 문서는 HTML + Excel, 최신 사용자 결정은 React + Agent Builder API. 기술 선택은 최신 결정 우선.
6. **4단계 지원:** 제안서와 최신 답변에는 4단계까지 있으나 초기 시연 화면에는 주로 1~3단계가 등장. 이번 목표는 화면에 필요한 범위 먼저 구현.

## 6. 개발 중 확정이 필요한 경우의 처리 규칙

- 실제 화면 UI 구조 확인이 필요하면 **HTML 원본**을 확인한다.
- 업무 판단 기준의 구버전과 최신버전이 다르면 **간호부 2026-11-16 답변**을 우선한다.
- 숫자가 서로 다르면 **동일 시각, 동일 시나리오, 동일 데이터셋**인지 확인한다.
- 데이터가 없는 경우 임상 사실처럼 꾸며 넣지 않는다. `TODO: nurse-review` 또는 `시연용 임시값`으로 관리한다.
- 1차 화면 완성에 필수적이지 않은 규칙은 후순위로 미룬다.
