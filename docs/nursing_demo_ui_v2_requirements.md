## 1. 작업 배경과 목표

현재 프로젝트는 원내 AI 경진대회 발표용 프로토타입이다. 이전 작업에서 최신 Claude Artifact 기반 UI와 계산 로직을 React에 재현했지만, 화면에 환자 및 처방 정보가 밀집해 있어 핵심인 **간호사별 업무 상태 파악 → 지원 필요 인지 → 지원자 추천 → 배정 및 응답 → 지원 진행 → 기록**의 흐름이 쉽게 보이지 않는다.

이번 단계는 원본과 동일하게 만드는 단계가 아니다. **실제 발표 상황을 고려해 화면을 간소화하고 우선순위를 재배치하는 UI 및 시연 흐름 개편 단계**다.

### 우선순위
1. **P0: 시연 핵심** — 간호사별 업무 상태, 지원 필요 알림, 추천 근거, 지원 배정과 수락/거절, 진행 및 기록
2. **P1: 보조 판단** — 환자 및 처방 상세, 인력 적정성, 구역별 처방 대기 현황
3. **P2: 보조 시연** — 시간 진행, 임의 처방 및 응급 이벤트, 분류 기준표, 개발 기준 설명

### 성공 조건
- 첫 화면에서 5초 내에 **누가 바쁘고 누가 지원 가능한지** 판단할 수 있다.
- 1~2분 시연으로 **지원 추천 → 배정 요청 → 간호사 확인 및 수락 또는 거절 → 상태 반영 → 기록**을 자연스럽게 보여줄 수 있다.
- 불필요한 숫자와 긴 문구를 제거하되 실제 필요한 환자 및 처방 정보는 상세 영역에 보존한다.
- 백엔드, Agent Builder, 실제 병원 데이터 연동은 **이번 범위에 포함하지 않는다**.
- UI 변경으로 기능별 계산 결과와 상태가 어긋나지 않는다.

## 2. 화면 레이아웃 및 정보 구조

### 2.1 권장 레이아웃 (데스크톱)

```text
[서비스 제목]                         [시연 시각] [현재 보기: 리더 ▼]
[간호사 상태 요약: 높음 N명, 지원 대기 N건] [시연 제어 ▼]

┌──────────────────────────────────────┬─────────────────────────┐
│ 간호사별 업무 현황                   │ 지원 필요 및 간호사 추천 │
│                                      │                         │
│ [간호사 카드] [간호사 카드]           │ [긴급/지원 요청 요약]    │
│ [간호사 카드] [간호사 카드]           │ [추천 1순위와 선정 근거]  │
│ [간호사 카드] [간호사 카드]           │ [추천자 변경/배정 요청]  │
│                                      │ [응답 대기/수락/진행]    │
├──────────────────────────────────────┼─────────────────────────┤
│ [인력 적정성 요약] [구역별 처방 현황] │ 최근 지원 활동, 전체 보기│
└──────────────────────────────────────┴─────────────────────────┘
[시연 기준 안내] [처방 분류 기준]  (텍스트 링크 → 모달)
```

- 지원 추천은 작은 사이드 카드가 아니라 **간호사 현황과 동등한 핵심 영역**으로 강조한다.
- 1366px 수준의 노트북에서 카드나 본문이 지나치게 좁지 않도록 기본은 간호사 카드 2열을 권장한다. 화면 폭이 충분할 때에만 3열을 검토한다.
- 작은 화면에서는 추천 영역을 카드 목록 위 또는 아래로 자연스럽게 배치하되 중요도를 유지한다.
- 인력 적정성과 구역별 처방 현황은 핵심 시연을 방해하지 않도록 간결한 보조 패널로 배치한다.
- 무의미한 애니메이션, 과한 그림자, 복잡한 차트, 장식용 아이콘을 추가하지 않는다.
- 상태 색상은 기존 청록색 및 초록, 주황, 빨강 계열을 활용하고, 반드시 **문자 라벨**도 제공한다.

### 2.2 헤더와 시연 제어, 사용자 전환

**문제:** 현재 `보기` 드롭다운과 모든 시연 버튼이 같은 줄에 있어 역할 전환이 잘 보이지 않음.

**변경:**
- 헤더 우측에 `현재 화면: 근무조 리더 ▼`를 명확히 표시한다. 선택 가능한 화면은 리더, 응급전문간호사, 개별 간호사로 유지한다.
- 로그인이나 실제 인증처럼 보이게 만들지 않는다. **시연을 위한 화면 전환**이다.
- 시간은 현재 헤더 시계처럼 눈에 띄게 유지한다.
- `+15분`, `자동 진행`, `처방 발생`, `간호요구 급증`, `CPCR 발생`, `초기화`는 `시연 제어` 버튼을 눌러 펼치는 영역으로 재배치한다. 발표 중 자주 쓰는 `+15분`은 접근하기 쉽게 배치해도 좋다.
- `초기화`는 실수 클릭 방지 확인을 고려하되 시연 방해가 없도록 간단하게 처리한다.
- 시연 버튼 때문에 화면이 세로로 크게 밀리지 않도록 한다.
- 장기적으로 재현 가능한 고정 시나리오를 추가할 수 있게 설계하되, 이번 단계에서 기존 이벤트 기능은 임의로 삭제하지 않는다.

## 3. 간호사 대시보드 카드

### 3.1 카드 최상단 정보

| 현재 화면 | 변경 요구 | 표시 예시 |
|---|---|---|
| 현재 업무량 | **담당 업무량** 또는 **담당 업무량(분)**으로 수정 | `담당 업무량 127분` |
| 관찰 40, 활력 4 | 이 두 항목을 **카드 요약 영역에서 제거** | 표시 안 함. 내부 계산은 유지 |
| 대기 처방 83 | **처방 수행 대기 상태**를 직관적으로 표시. 소요시간(83분)과 실제 대기시간(40분)이 혼동되지 않게 구분 | `수행 대기 3건`, `가장 오래 대기 40분` |
| KTAS 정보 | **KTAS 1, 2등급 환자 수를 눈에 띄는 배지나 간결한 통계 형태로 추가** | `KTAS 1 0명` `KTAS 2 1명` |
| 1시간 뒤 예측 | 완전히 제거 | 예측 수치, 옅은 막대, 예측 설명 및 예측 알림 제거 |
| 업무 단계 | 유지하고 시각적 우선순위 상향 | `높음 / 보통 / 여유` |

**주의 사항:**
- `대기 처방 83분`은 원본에서 **미완료 처방의 표준 예상 소요시간 합계**이지, 처방 후 경과시간이 아니다. 숫자만 `대기시간 83분`으로 바꿔 표시하면 잘못된 정보가 된다.
- 화면에서 `수행 대기 N건` 및 `최장 대기 N분`처럼 **실제로 계산할 수 있는 값**으로 바꿔 표시한다.
- `담당 업무량`은 기존 `loadOf()` 계산 결과를 표시한다. KTAS와 NEWS, 활력, 처방 소요시간 관련 계산을 이번 단계에서 임의로 제거하거나 변경하지 않는다.
- KTAS 1등급, 2등급 환자가 0명이어도 `0명`을 표시할지 숨길지는 카드 높이를 고려해 일관된 규칙으로 적용한다. 기본안은 간결한 두 개의 배지다.

### 3.2 환자별 정보와 처방 내역

- 환자 목록을 기본적으로 간단한 행이나 카드로 표현하고, 환자를 펼치면 처방 상세와 수행 조작이 보이도록 한다. 단, 초기 시연에서 핵심 환자의 대기 처방은 쉽게 접근 가능해야 한다.
- 환자 한 행의 우선 표시 정보: `환자명`, `환자 식별자(1-01 등)`, `KTAS`, `NEWS`, `활력 주기`, `대기 중 처방 건수`.
- `활력 2시간마다` 대신 **`활력 주기: 2시간`**으로 변경하고, 30분 이하 주기에도 자연스럽게 대응한다.
- `1구역 01병상`처럼 `1-01`과 겹치는 위치 정보는 반복하지 않는다.
- 가상 등록번호는 환자명 옆이나 아래에 작은 보조 텍스트로 보여주되 긴 정보 줄을 만들지 않는다.
- 처방 행은 기본적으로 **`처방명 | 대기 40분 | 수행 | 확인중`** 정도로 간결하게 표현한다.
- **처방별 표준 소요시간 및 수행 목표시간을 환자별 처방 행에서 제거한다.** 예: `수혈(PRBC) 25분, 대기 40/기준 30분` → `수혈(PRBC) | 대기 40분`.
- 예정 처방은 대기 중인 처방과 구별하여 `예정 09:40` 등의 작은 상태로 표시한다.
- 환자 전체를 한번에 펼쳐야만 버튼이 동작하는 등 발표 동선을 길게 만들지 않는다. 펼침 상태의 기본값은 시연에 유리하게 조정한다.

### 3.3 신규 `확인중` 처리: 반드시 상태로 구현

현재 원본의 `ArtifactOrder`는 완료 여부를 `orders` 배열에서 제거하는 방식으로 관리하고 있고, `확인중` 상태가 없다. 이번 작업에서 **처방 상태 관리**를 추가한다.

**상태 정의**

| 상태 | 의미 | 대시보드 표시 | 조작 |
|---|---|---|---|
| `pending` | 처방 발생 후 수행 전 대기 | `대기 40분` | `수행`, `확인중` |
| `acknowledged` | 처방 확인 완료, 수행은 아직 하지 않음 | `확인중`, 확인 시각 표시(간결하게) | `수행`, `대기로 복귀` |
| `completed` | 수행 완료 | 진행 중 목록에서 제외 | 필요 시 완료 기록만 확인 |

**상태별 계산과 UI 반영**

1. `확인중` 클릭 시 `pending → acknowledged`로 전환하고, 처방을 삭제하지 않는다.
2. 확인중인 처방은 **활성 수행 대기 건수, 최장 대기시간, 처방 지연 집계 및 지연으로 인한 지원 알림 조건에서 제외**한다.
3. 확인중인 처방은 `확인중 N건`으로 별도로 집계하거나 환자 상세의 별도 그룹에 표시한다.
4. `수행` 클릭 시 상태에 관계없이 완료 처리를 하고 활성 목록에서 제거한다. 기존 수행자 기록 및 지원 간호사의 대리 수행 기록은 유지한다.
5. `대기로 복귀` 시 다시 대기 대상에 포함한다. **원래 처방 발생시각(`at`)은 보존**한다. 실제 경과시간을 임의로 되돌리거나 멈춘 것처럼 기록하지 않는다.
6. **중요한 계산 정책:** `acknowledged`는 완료가 아니므로 **기존 담당 업무량 계산에서 해당 처방의 표준 소요시간을 일단 유지**한다. 단, 시간 기반 대기 및 지연 집계에는 제외한다. 이 정책은 발표용 1차안이며, UI의 `담당 업무량`과 `수행 대기` 숫자가 다르게 움직이는 이유를 결과 문서에 명시한다.
7. 별도 백엔드 없이 Zustand 시연 상태에서 관리하고 `초기화`하면 원본 초기 상태로 돌아간다.
8. 추후 Agent Builder 또는 실제 병원 시스템으로 연결할 때 상태 의미가 혼동되지 않도록 타입 정의와 함수 이름을 명확히 한다.

**기존 로직과의 연결:** `loadOf`, `zoneTimeliness`, `buildAlerts`, `completeOrder`, `OrderRow`, store 액션에 모두 영향이 있다. 한 곳에서만 `확인중`을 숨기는 방식으로 구현하지 않는다.

### 3.4 `초과` 개념 처리

현재 화면에 보이는 `수행 기준 초과 N건`이나 `기준 초과`는 원본의 **임시 수행 목표시간**으로 계산된다. 사용자는 아직 수행 시간과 목표 기준을 확정하지 못했으므로 발표 화면에서 확정된 지표인 것처럼 강조하지 않기를 원한다.

- **처방 행, 간호사 카드 및 구역별 요약에서 목표시간과 초과 수치 표현을 기본 화면에서 제거**한다.
- `구역별 처방 적시성`은 이번 단계에서 **`구역별 처방 대기 현황`**으로 표현하는 것을 권장한다. 표시값: 대기 건수, 최장 대기시간, 확인중 건수(공간이 허용된다면).
- 기존 `dueOf`와 임시 기준 설정값은 추후 검토를 위해 코드에 보존하되, **초과 기준을 사용한 알림이 그대로 노출되지 않도록** UI 및 `buildAlerts`의 해당 트리거를 함께 검토한다.
- 시연용 대체 기준으로는 이미 코드에 존재하는 **업무 단계 '높음', 지원 필요 직접 요청, 높음 지속시간, 간호요구 급증** 등의 조건을 우선 활용한다. 새로운 임상 기준이나 임계값을 임의로 만들지 않는다.
- 원본의 09:00 초기 알림 3건이 변경될 수 있다. 이는 요구사항 변경에 따른 정상적인 변화일 수 있으므로, 변경 전후 조건과 결과를 `docs/result/`에 문서화한다.

## 4. 지원 필요 알림 및 지원 간호사 추천: 최우선 기능

### 4.1 위치 및 시각적 우선순위

- `SupportAlertPanel`을 메인 대시보드의 **두 번째 핵심 축**으로 배치한다. 카드, 타이틀, 추천 근거 및 주요 버튼이 눈에 잘 띄어야 한다.
- `지원 필요 알림` 목록의 각 항목은 짧고 구조화된 문구로 변경한다.
  - 예: `김서연 | 업무 단계: 높음` / `지원이 필요한 간호사` / `추천: 한지호 (여유)`.
- 원본의 긴 문장(`근무조 리더간호사, 응급전문간호사: 근무조 지원 또는 환자 재배정`)은 자세한 설명 영역으로 이동하거나 요약한다.
- 3단계 인력 적정성 경고, CPCR 알림처럼 성격이 다른 이벤트는 단순 지원 요청과 구분한다. 가장 중요한 지원 배정 액션이 긴급 경고 속에 묻히지 않도록 한다.

### 4.2 추천 후보 표시

- 간호사별 지원 요청에서 **추천 1순위 간호사**를 크게 표시한다.
- 선정 근거를 2~3개 요약 정보로 보여준다. 실제 원본 `recommendNurse()`가 확인하는 데이터만 사용한다.
  - 예: `현재 단계: 여유`, `담당 업무량 0분`, `현재 다른 지원 없음`.
- 추천 후보를 **직접 변경할 수 있는 선택 UI**를 제공한다. 추천 순위가 낮더라도 유효한 간호사를 수동 지정할 수 있게 한다.
- 기본 추천 결과는 기존 정렬 규칙 `여유 우선 → 현재 업무량 적은 순`을 유지한다.
- 후보 제외 조건: 본인, 지원 중이거나 이미 배정 대기 중인 사람, 높은 업무 단계, 우선 대상자, 해당 요청에 대해 거절한 사람. UI 목록과 **액션 함수 내부 검증이 같아야 한다**.
- 추천 불가 시 버튼을 없애는 것으로 끝내지 말고, `지금 배정 가능한 지원자가 없습니다` 등 명확한 빈 상태를 표시한다.

**표현상 주의:** 현재 추천은 JavaScript의 **규칙 기반 기능**이다. 추천 결과를 시연에서 크게 강조하는 것은 좋지만, Agent Builder API나 LLM이 아직 연결되지 않았다면 `실시간 AI 분석 완료`처럼 구현하지 않은 기능이 작동한 것으로 표시하면 안 된다. 기본 문구는 **`지원 간호사 추천`**, **`업무량 기반 추천`**, **`추천 1순위`**를 사용한다. 추후 Agent Builder 연동 후 실제 연결 상태를 기반으로 발표 문구를 확장할 수 있도록 컴포넌트를 설계한다.

### 4.3 메인 지원 시나리오 상태 흐름

**시연 중 전체 상태가 눈에 보여야 한다.** 추천 카드 또는 지원 진행 패널에 현재 단계를 표시한다.

```text
[지원 필요]
   ↓
[지원자 추천] → [다른 간호사 선택 가능]
   ↓
[배정 요청]
   ↓
[간호사 응답 대기]
   ├── [수락] → [지원 진행] → [대상자와 지원자 카드에 동시 표시]
   │                           ↓
   │                    [수행 내용 기록] → [지원 종료] → [누적 기록]
   └── [거절] → [거절 이유 기록] → [다음 후보 추천/재배정]
```

**상세 요구사항**
1. 리더 화면에서 지원 대상, 추천자, 추천 근거, 수동 변경 및 배정 요청을 한 화면에서 확인할 수 있어야 한다.
2. `배정 요청` 시 **즉시 지원 완료로 취급하지 않고** `응답 대기`로 표시한다.
3. 헤더의 역할 전환을 통해 해당 간호사 화면으로 바꾸면 **수락 및 거절 요청 카드**가 뚜렷하게 보여야 한다. 거절 사유는 기존 선택지(휴식, 중증 환자 전담, 다른 업무) 유지.
4. `수락` 시 대상 간호사 카드에 `한지호 지원 중`, 지원 간호사 카드에 `김서연 지원 중` 등 상호 참조를 표시한다.
5. 지원 수락 이후에만 기존 감산 로직을 적용한다. 임시 계산식은 바꾸지 않는다.
6. 수락한 지원자가 대상 간호사의 처방을 수행하면 **수행자 귀속 및 지원 수행 건수**를 기록한다.
7. `지원 종료` 후에는 진행 중 표시를 제거하고 기록에는 남긴다.
8. `거절` 시 기존 후보 제외 이력을 반영해 **다음 추천 후보를 자동 계산**하고 추천 결과를 새로 표시한다.
9. 동일 간호사의 중복 배정, 자신을 지원자로 지정하는 행위, 이미 지원 중인 간호사에 대한 잘못된 재요청을 **액션 로직 레벨**에서 막는다.
10. 카드와 패널이 현재 상태에 모순된 정보를 표시하지 않도록 단일 스토어를 기준으로 업데이트한다.

### 4.4 지원 카드에 필요한 상태 표시

- `추천 중`, `응답 대기`, `수락됨 / 지원 중`, `거절됨 / 다른 후보 추천`, `종료`를 색상과 텍스트로 명확히 구분한다.
- 단계 표시가 지나치게 복잡한 스텝퍼라면 `현재 단계 + 다음 행동 버튼`의 간결한 구조로 바꿔도 된다.
- `배정 요청`은 추천 후보 이름을 포함하는 분명한 Primary 버튼으로 표시하고, 일반 버튼과 차이를 둔다.
- 지원 요청의 주체(대상 간호사)와 지원할 사람(추천 간호사)을 서로 혼동하지 않도록 레이블을 명확히 한다.

## 5. 지원 기록

- 지금은 오른쪽 작은 테이블로 되어 있어 누적성과 흐름이 잘 보이지 않는다.
- 메인 화면에서는 **최근 지원 활동 3~5건**을 시간순 또는 최신순으로 보여주고, `전체 지원 기록`을 누르면 모달이나 별도 뷰에서 누적 이력을 확인하도록 한다.
- 누적 이력에는 `요청/배정`, `수락`, `거절`, `진행`, `수행`, `종료` 등이 시간순으로 정리되도록 한다.
- 기존 `supports`, `decline`, `done` 상태를 최대한 재사용한다. 필요한 경우 시연용 `activityLog`를 별도 상태로 관리하되 중복 계산과 이중 기록을 방지한다.
- 임의 이벤트를 발생시켰다고 가짜 기록을 사전에 쌓아 놓지는 않는다. **실제 시연 조작 결과가 누적되는 것처럼** 보여야 한다.
- 초기 상태가 비어 있을 때는 빈 상태 문구를 짧게 표시한다.
- 기록 데이터가 세션 메모리에만 남는다면, **새로고침 시 사라질 수 있다는 제한**을 결과 문서에 명시한다. 지속성 저장은 이번 범위에서 필수는 아니다.

## 6. 인력 적정성 및 구역별 처방 대기 현황

### 인력 적정성
- 작은 보조 요약 카드로 유지: `현재 근무조 업무량 / 인력 기준`, `적정/주의/초과`.
- 이전 코드의 인력 기준은 **환자 담당 간호사 수 × 50분**이다. 확정된 임상 기준으로 오인되지 않도록 조심하고 수치는 임의 변경하지 않는다.
- 필요 이상으로 크고 화려한 그래프는 만들지 않는다.

### 구역별 처방 현황
- 명칭은 `처방 적시성` 대신 **`구역별 처방 대기 현황`** 권장.
- 주요 지표: 구역, 수행 대기 건수, 최장 대기시간, 가능하다면 확인중 건수.
- 아직 확정되지 않은 목표시간을 기준으로 한 `기준 초과` 열은 기본 화면에서 제거한다.
- 대기시간은 **처방 후 현재까지 경과시간**으로 계산한다. `확인중`은 활성 대기 집계에서 제외한다.
- 시연 시각을 진행하면 대기시간과 현황이 일관되게 갱신되어야 한다.

## 7. 처방 분류 기준표와 하단 장문 안내

- `OrderCatalogPanel`은 메인 대시보드에서 제거한다. 단, **데이터 및 로직은 삭제하지 않는다**.
- 푸터에 `처방 분류 기준` 텍스트 링크를 두고, 클릭 시 모달에서 확인할 수 있게 한다.
- 하단 긴 `가상 데이터로 만든 시연판이며 ...` 안내문은 **본문에서 제거**하고 `시연 기준 안내` 링크를 통해 모달로 확인하도록 한다.
- 법적이나 운영상 필요한 경고를 삭제해 숨기기보다는, 과도한 장문 노출을 피하면서 **정확한 기준 설명에는 접근 가능**하도록 설계한다.
- 발표용 화면에 출처 없는 홍보 문구나 불필요한 주석을 늘어놓지 않는다.

- 구현 중 불명확한 판단 기준이 있으면 **안전한 시연 가정과 선택 이유를 결과 문서에 기재**한다. 새 임상 규칙을 임의로 확정하지 않는다.

| T04 | 확인중 처방 `대기로 복귀` | 원래 발생시각 보존, 활성 대기 집계에 복귀. 시연 시각 기준 경과시간 정상 표시 |
| T05 | 확인중 처방 `수행` | 활성 목록에서 제거, 완료 및 수행자 기록 반영. 이중 수행 불가 |
| T06 | 지원 필요 알림 | 업무 단계 및 직접 요청 등 정의된 조건에 따라 지원 패널이 갱신됨. 임시 초과 기준을 확정 지표처럼 표시하지 않음 |
| T07 | 추천 후보 변경 | 기본 추천 1순위와 수동 선택 UI 동작. 제외 조건에 해당하는 간호사는 선택/배정 불가 |
| T08 | `배정 요청` | 요청 직후 `응답 대기`, 지원 감산 아직 없음, 배정 카드 및 기록 갱신 |
| T09 | 해당 간호사 화면 전환 및 `수락` | `지원 중`으로 변경, 대상/지원자 카드에 상호 표시, 지원 감산은 이때만 반영 |
| T10 | 지원 수행 및 종료 | 대리 수행자와 수행 건수 기록, 종료 후 진행 상태 해제 및 누적 기록 유지 |
| T11 | 지원 요청 `거절` | 거절 이유 기록, 해당 후보 제외, 다음 적격 후보 추천, 재배정 가능 |
| T12 | 15분 시연 진행 | pending 처방의 대기시간 증가. acknowledged는 활성 대기 집계에 포함되지 않음 |
| T13 | 화면 보기 전환 | 리더 및 개별 간호사 화면이 요청 상태, 수락/거절 조작, 접근 범위에 따라 올바르게 보임 |
| T14 | 푸터 링크 | 시연 기준 설명과 처방 기준이 모달에만 표시되고 닫기 및 키보드 동작 가능 |
| T15 | 주요 반응형 | 1366x768, 1440x900, 1920x1080 및 좁은 화면에서 주요 버튼, 추천 영역, 카드가 겹치지 않음 |
| T16 | 초기화 | 확인중, 배정, 지원 기록 등 모든 임시 시연 상태가 초기 상태로 복원되고 자동 진행도 종료 |
| T17 | `npm test`, `npm run build` | 실제 실행 결과 기록. 오류 및 경고 내용도 함께 기록 |

**테스트 갱신 주의:** 기존 테스트는 초기 알림 3건, 초기 처방 지연 수치 등을 기대한다. 새로운 UX와 상태 정책으로 달라진 조건을 억지로 이전 결과에 맞추지 말고, 변경 이유와 새 기대값을 문서화하고 테스트를 수정한다. 기존 F2 테스트는 회귀를 확인한다.

## 11. 작업 결과 문서화: `docs/result/` 필수

작업을 완료했다고 말하기 전에 **`docs/result/`에 다음 문서와 확인 자료를 생성**한다. 디렉터리가 없으면 생성한다.

### 필수 문서
1. `docs/result/README.md`
   - 이번 개편의 목적, 최종 결과, 문서 목록, 다음 검토 순서
2. `docs/result/ui_revision_change_log.md`
   - 기능별 변경 전/후, 구현 파일, UI 위치, 기존 동작 영향, 제거 및 보류 항목
   - 사용자 요구 0~8번의 **반영 여부 매핑 표** 포함
3. `docs/result/ui_revision_logic_decisions.md`
   - `확인중` 상태 정의와 업무량/처방 대기/알림 집계 영향
   - 추천 후보 필터링과 수동 변경 규칙, 수락 및 거절 상태 전이
   - 제거한 1시간 예측과 임시 초과 기준의 영향
   - 미확정 임상 기준, 구현 가정 및 이유, 향후 간호부 확인 필요사항
4. `docs/result/ui_revision_test_report.md`
   - 실행 명령, 테스트 개수와 결과, 빌드 결과, 수동 시연 결과
   - T01~T17 테스트 시나리오별 PASS/FAIL/미실행 및 근거
   - 테스트하지 못한 항목, 알려진 오류, 재현 단계
5. `docs/result/demo_walkthrough.md`
   - 1~2분 발표 시연 흐름: 시작 화면 → 지원 필요 선택 → 추천자 선택 → 배정 → 지원자 화면 전환 → 수락/거절 → 지원 중 표시 → 지원 종료/기록
   - 화면별 클릭 대상, 예상 상태 및 문구, 초기화 방법

### 권장 자료
- 가능한 경우 변경 전/후 스크린샷을 `docs/result/screenshots/` 아래에 저장한다. 자동 스크린샷이 불가능하면 실행 가능한 캡처 방법과 확인한 뷰포트 크기를 기록한다.
- 적용할 수 없었던 요구사항이나 정책 충돌은 누락하지 말고 **미완료 및 확인 필요**로 기록한다.
- `docs/result/` 기록은 **개발을 끝낸 후 한 번에 추측해서 쓰지 말고** 실제 수정한 파일과 검증 결과를 기반으로 작성한다.

## 12. 단계별 작업 계획

1. **현행 분석:** 기존 소스와 이 문서를 대조해 영향 범위 및 레이아웃 수정 계획을 세운다.
2. **핵심 로직:** `확인중` 상태와 대기 집계, 지원 후보 선택과 전이부터 안정적으로 구현한다.
3. **UI 재구성:** 카드 정보 줄이기, 지원 추천 패널 강조, 역할 전환, 보조 패널 축소, 모달 이동.
4. **시연 검증:** 실제로 역할을 바꾸며 배정, 수락, 거절, 기록까지 수동 검증한다.
5. **회귀 테스트:** 기존 F2 및 원본 재현 테스트가 의도한 변경을 제외하고 정상 유지되는지 확인한다.
6. **문서 작성:** `/docs/result`에 변경 목록, 정책, 테스트, 발표 동선을 빠짐없이 남긴다.

**작업 종료 기준:** UI만 예쁘게 바뀐 상태가 아니라, **추천 → 배정 → 확인/수락 또는 거절 → 진행 → 기록**이 실제로 작동하고 테스트와 상세 결과 문서가 작성되어야 한다.
