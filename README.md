# 간호업무량 기반 실시간 간호지원체계

> 응급실 간호업무 현황을 가상 데이터로 재현하는 **1차 웹 프로토타입**
>
> 기술 구성: **React + TypeScript + Vite + Zustand + Agent Builder(Langflow 기반) Flow API**
>
> 현재 작업: **React 화면 및 시나리오 구현 우선**, Agent Builder API는 후속 연결

## 1. 이 프로젝트가 해결하려는 문제

담당 간호사의 업무량은 환자 상태, 처방 발생, 수행 여부, 활력징후 측정 주기 등으로 계속 변한다. 기존에는 근무 책임간호사가 현장을 직접 확인하거나 구두 지원 요청을 받아 과부하를 파악해야 했다.

이 시제품은 **간호사별 예상 업무량과 수행 대기 처방을 한눈에 보여주고, 지원이 필요하면 근무 책임간호사가 지원자를 정하고 그 결과를 기록하는 흐름**을 시연한다. 업무량은 개인 성과 점수가 아니라 **담당 환자와 업무가 요구하는 양**으로 이해해야 한다.

**중요:** 본 프로젝트는 실제 임상 판단용 시스템이 아니다. 실제 환자정보, 실시간 AMIS 연동, 운영 환경 수준의 보안과 데이터 동기화는 포함하지 않는다.

## 2. 단계별 범위

| 구분 | 범위 |
| --- | --- |
| **1차: 지금 구현** | React 현황판, 가상 데이터, 시간 진행, 처방 수행, 환자 상태 변화, 업무량 표시, 처방 지연, 지원 요청 및 추천, 배정, 수락 및 거절, 지원 종료, 지원 기록 |
| **1차: Agent Builder 연동 예정** | F1 처방 분류, F2 업무량 산정, F3 처방 지연 판단, F4 지원 필요 판단 및 추천을 각각 API로 연결 |
| **2차: 이번에 구현하지 않음** | 실제 AMIS 연동, SR 또는 IRB 기반 데이터 수집, 임상 기준 검증, AI 기반 1~2시간 뒤 업무량 예측, 장기간 학습과 통계, 병동 및 ICU 확장, 다중 사용자 실시간 동기화 |

기존 HTML과 PDF에는 `1시간 뒤 예상 업무량` UI가 보일 수 있다. **화면 재현을 위해 시연용 표시값으로 남길 수 있으나, AI 예측 기능을 구현했다고 표현하면 안 된다.** 화면에서 `시연용 값`임을 구분하거나 별도 표시를 검토한다.

## 3. 기술 아키텍처

```text
정적 React 웹앱 (빌드 후 Nginx 등으로 배포 가능)
├─ UI 컴포넌트 및 화면 전환
├─ JSON 샘플 데이터 / 시나리오 이벤트
├─ Zustand 상태 관리 (옵션: localStorage 저장)
├─ 프론트엔드 동작
│  ├─ 시연 시간 진행, 시작 상태 초기화
│  ├─ 처방 완료 처리
│  ├─ 지원 요청, 배정, 수락, 거절, 종료 상태 처리
│  └─ 지원 기록과 표시 갱신
└─ 서비스 계층: EvaluationService
   ├─ 초기: MockEvaluationService
   └─ 추후: LangflowEvaluationService
      ├─ F1 처방 분류
      ├─ F2 업무량 산정
      ├─ F3 처방 지연 판단
      └─ F4 지원 필요 판단 및 추천

Agent Builder (기존 연구실 서버): Flow별 실행 API 제공
별도의 FastAPI 백엔드 및 운영용 DB: 1차 범위에서 제외
```

**설계 원칙:** React는 화면과 시연 상태의 기준 데이터(원본 상태)를 관리한다. Agent Builder는 데이터를 받아 계산하거나 판단한 **결과만 반환한다.** Flow가 React의 간호사 및 처방 상태를 직접 수정하거나 저장하도록 설계하지 않는다.

정적 프론트엔드는 API 접근 권한과 CORS가 허용된 환경에서 Flow를 직접 호출할 수 있다. 하지만 **영구 API Key를 프론트엔드 코드나 `VITE_` 환경변수에 넣지 않는다.** 향후 실제 연결 시 병원 내 인증 정책에 맞는 안전한 호출 방식을 결정한다. 이번 화면 개발에서는 Mock 모드로 충분하다.

우선순위는 **간호부 최신 답변의 업무 규칙 → 기존 HTML의 실제 화면과 동작 → 시연 PDF의 화면과 순서 → 제안서의 설계 의도 → 엑셀 예시값**으로 이해한다. 단, 데이터 수정값이 새로 제공되면 **해당 데이터 항목에는 수정값을 우선 적용**한다. 다른 자료에 없는 계산식을 임의의 임상 기준으로 만들어 넣지 않는다.

자료별 페이지와 불일치 사항은 [`docs/REFERENCE_AND_DECISIONS.md`](docs/REFERENCE_AND_DECISIONS.md)를 참고한다.

## 5. 시연 화면의 구성

### 5.1. 근무 책임간호사 현황판

- 상단: 프로젝트명, 근무조(D 근무 등), 시연 현재 시각, 화면 전환, 시연 동작 버튼
- 본문: 간호사별 카드. 담당 구역, 담당 환자 수, 업무량 단계, 관찰 및 활력, 대기 처방, 현재 업무량, 처방 초과 건수, 환자별 처방 목록
- 환자 정보: 환자 가상 코드(A-01 등), KTAS, NEWS, 활력징후 측정 주기, 처방 목록
- 오른쪽: 지원 알림, 근무조 전체 업무량과 인력 적정성, 구역별 처방 적시성, 지원 기록, 처방 분류 기준
- 상호작용: 처방 수행, 지원 필요 표시, 우선 대상 지정(권한에 따라), 추천 및 배정, 지원 종료

### 5.2. 일반 간호사 보기

- **본인 담당 환자 및 처방의 상세 정보만 노출**
- 동료 간호사의 상세 업무량 및 환자 정보는 보여주지 않고 **업무량 단계만 공유**
- 지원 배정 알림 확인, 수락 및 거절(사유 선택), 본인 지원 업무 확인은 이번 시제품에서 시연 가능하도록 구현
- 권한은 1차에서 **UI 데모 모드**로 재현하며, 실제 인증과 보안을 구현했다고 주장하지 않음

### 5.3. 역할별 카드

- 김서연, 박도윤, 이하은, 최민준: 환자 담당 카드
- 정유나(Pre-T), 한지호(물품관리): 별도 역할 카드
- 역할별 기본 단계는 환자 담당자의 계산식과 동일하다고 가정하지 않는다. 화면에 없는 데이터를 임의로 추가하지 않는다.

## 6. 업무량 및 시간 개념

같은 `분`이라도 의미가 전혀 다르므로 별도의 데이터 필드로 관리한다.

| 항목 | 뜻 | 계산 및 표시 원칙 |
| --- | --- | --- |
| **관찰 업무량** | 환자 관찰에 필요한 예상 업무시간 | 초기에는 기존 시연값 활용. KTAS 또는 NEWS별 산정식은 합의되지 않았으면 자동 계산하지 않음 |
| **활력 업무량** | 활력징후 측정 관련 예상 업무시간 | 초기에는 기존 시연값 활용. 주기별 자동 계산은 기준이 명확해진 뒤 추가 |
| **대기 처방 업무량** | 미완료 처방의 **예상 수행시간 합계** | 처방별 예상시간 합산. `처방 대기 경과시간`과 다름 |
| **현재 업무량** | 관찰 + 활력 + 대기 처방의 예상 수행시간 합계 | 기본 화면에서는 이 세 값으로 합산 |
| **처방 대기 경과시간** | 처방이 발생하고 아직 수행되지 않은 경과시간 | 일반 처방은 발생시각부터, 예정 처방은 예정시각부터 계산 |
| **처방 수행 기준시간** | 처방 유형 및 긴급도에 따라 정해진 목표 수행시간 | 시연값 또는 확인된 설정값 사용 |
| **수행 기준 초과** | 경과시간이 목표 수행시간을 초과 | 수행 기준 초과 건수에 집계 |

**수행 중 처리:** 기존 UI에는 수행 중 진행률이 없고 `수행` 버튼이 있다. 1차에서는 `대기 → 완료`로 단순화하고 완료 시점까지 미완료 업무량에 포함한다. 수행 중 실제 잔여시간 추정은 구현하지 않는다.

### 예시: 화면 값 검산

시연 PDF 2페이지 09:00은 김서연 135분(관찰 40, 활력 12, 대기 처방 83), 박도윤 34분, 이하은 59분, 최민준 13분이다. 같은 환자로 HTML 식을 돌리면 관찰만 달라 136, 34, 60, 11이 된다. 활력, 대기 처방, 네 명의 합 241분은 같다. 카드는 HTML 식을 유지하고 PDF 합계로 덮어쓰지 않는다. PDF 7페이지의 김서연 143분(관찰 45, 활력 15, 대기 처방 83)은 09:45 화면이라 09:00과 섞지 않는다.

### 업무량 단계와 인력 기준은 서로 다른 개념

- **간호사 카드 업무량 단계:** 시연용 여유, 보통, 높음. 과거 30분 및 50분 경계값을 사용했으나 추후 보정 가능한 설정값으로 분리한다.
- **근무조 인력 적정성 및 지원 판단 기준:** 간호부 답변에 따라 **담당 환자 1명당 50분**을 기준으로 한다. `담당 환자 수 × 50분`과 산정 업무량을 비교한다. 50분은 시연용 임시값이다.
- 기존 화면의 `환자 담당 간호사 4명 × 50분 = 200분`은 **변경 전 계산법**이다. 새 구현에서 그대로 복사하지 않는다.
- 환자당 50분을 관찰 업무량에 다시 더하지 않는다. **비교용 기준**으로 사용한다.
- 기존 시연의 3단계 근무조 알림이 새 기준에서 더 이상 발생하지 않을 수 있다. 그 경우 이전 알림을 강제로 유지하지 말고 기준에 맞는 결과를 표시한다.

## 7. Agent Builder에서 구현할 4개 Flow

Flow는 각각 독립 실행 가능한 기능으로 설계한다. 프론트엔드의 서비스 어댑터는 동일한 입력 및 출력 타입을 이용해 Mock과 실제 API를 교체할 수 있도록 만든다.

| Flow | 입력 예시 | 출력 예시 | 1차 판단 원칙 |
| --- | --- | --- | --- |
| **F1 처방 분류** | 처방명, 유형, 긴급도, 시연 기준표 | 분류, 예상 소요시간 | 화면에 나오는 처방과 기준표 범위만 우선 구현 |
| **F2 업무량 산정** | 담당 환자, 관찰 및 활력 시연값, 수행 대기 처방과 F1 결과 | 관찰, 활력, 대기 처방, 합계, 단계 | 초기 관찰 및 활력은 샘플값, 대기 처방은 수행시간 합계 |
| **F3 처방 지연 판단** | 처방 발생 또는 예정시각, 수행 여부, 현재 시각, 기준시간 | 경과시간, 초과 여부, 구역별 집계 | 예정 처방은 예정시각 기준. 우선 대상 알림과 처방 마감시간을 혼동하지 않음 |
| **F4 지원 필요 판단 및 추천** | F2 및 F3 결과, 환자 악화 여부, 지원 요청, 근무자 상태 | 지원 단계, 이유, 추천 가능 간호사 | 지원자 추천은 참고용, 최종 배정은 근무 책임간호사가 결정 |

알림 단계는 간호부 답변의 1~4단계 정책을 참고하되, **현재 시연 화면에서 다루는 1~3단계를 먼저 동작**시킨다. 4단계 부서 간 지원 연동은 이번 범위에서 제외한다. 세부 지연시간이 합의되지 않았다면 `demoConfig`의 임시값으로 표현한다.

상세 API 계약과 TypeScript 모델: [`docs/TECH_SPEC.md`](docs/TECH_SPEC.md)

## 8. 개발 순서

1. **참고 자료 분석:** HTML, 시연 PDF, 제안서, 최신 Q&A의 화면, 데이터, 버튼, 변경사항 정리
2. **React UI 구현:** HTML에 가까운 시각적 구성, 카드, 표, 알림, 버튼과 모달
3. **가상 데이터 및 상태 관리:** Excel을 초기 JSON으로 변환, Zustand 상태와 시나리오 이벤트 설계
4. **Mock Flow 연결:** 실제 API와 동일한 인터페이스의 F1~F4 로컬 구현
5. **시연 흐름 구현:** 09:00 초기화, 지원 배정, 처방 수행, 지원 종료, 09:15 및 09:45 시간 진행, 환자 상태 악화, 역할 전환
6. **검증:** 화면 값 합계, 수행 완료 처리, 지연 건수, 지원 기록, 권한별 노출, 50분 기준 확인
7. **추후 API 연결:** Agent Builder에서 Flow가 준비되면 Mock 어댑터만 실제 어댑터로 교체

## 10. 실행

```bash
npm install

npm run build
```

개발 서버 기본 주소는 `http://localhost:5173`이다. 계산 모드는 `src/config/evaluationConfig.ts`의 `mode`이며 기본값은 `mock`이다. `langflow`로 바꾸면 명세가 없다는 오류를 보여 주고, Mock 결과를 실제 Flow 결과처럼 채우지 않는다.

## 11. 이번 구현 범위

포함:

- HTML 현황판의 툴바, 간호사 카드, 우측 패널, 시간 진행, 자동 진행, 처방 발생, 간호요구 급증, 초기화
- 처방 수행, 지원 추천, 다른 간호사 선택, 수락, 거절, 종료, 지원 기록
- 일반 간호사 보기에서 본인 상세와 동료 단계만 렌더링
- Mock F1~F4와 Langflow 어댑터 자리

HTML과 다르게 적용한 간호부 답변:

- 인력 기준은 담당 환자 수 x 50분. 09:00은 241분 / 450분, 적정이다. 구 3단계 초과 알림은 만들지 않는다.
- 우선 대상 10분은 지원 알림 판정에만 쓰고, 화면에 보이는 처방 목표시간은 유지한다.
- NEWS 화살표는 위험 단계가 오를 때만 표시한다. 09:00의 A-01은 5에서 6이라 화살표가 없다.
- 지원은 배정 후 지원 간호사가 수락해야 시작하고, 시작 시각은 수락 시각이다.
- 1시간 뒤 숫자는 시연용으로 표시한다. 계산은 Mock F2가 하고 카드는 그 결과를 보여 준다.
- 간호요구 급증의 첫 대상은 시연 PDF 7페이지에 맞춰 D-02다. HTML 파일의 순서는 D-01부터다.
- 업무량 단계와 환자 수 x 50분 초과는 따로 둔다. 09:00에 높음인 간호사도 개인 환자 기준은 넘지 않는다. 개인 초과를 지원 단계로 쓰지는 않는다.

분석과 미확정 항목은 `docs/HTML_ANALYSIS.md`, `docs/OPEN_QUESTIONS.md`에 있다. 엑셀 수정표와 답변 PPTX는 패키지에 없어 D열 수정값은 반영하지 못했다.

## 12. 파일 구조

```text
src/
  app/                 # 현황판 엔트리
  components/          # 공통 UI가 더 필요해지면 사용
  features/
    dashboard/         # 간호사 카드
    orders/            # 처방 행
    support/           # 알림, 배정, 기록, 우측 패널
    simulation/        # 시연 툴바
    f2/                # F2 API 개발용 패널
  data/fixtures/       # 초기 가상 데이터, 처방 규칙
  domain/              # 시연 시각, 관찰표, 시나리오, 지원 규칙
  services/
    evaluation/        # EvaluationService 경계
    mock/              # F1~F4 Mock
    f2/                # F2 v3 요청, 응답 해석, 상태 변환
    langflow/          # 명세 확정 전 자리
  store/               # Zustand
  config/              # demoConfig, 계산 모드
  styles/              # HTML 시연판 색과 배치
```

`src/components/`는 아직 비어 있다. 화면 조각은 `features/`에 있다.

## 13. Cursor 사용법

1. 이 패키지 전체를 React 프로젝트 루트에 복사한다.
2. 원본 HTML, PDF, PPTX, XLSX 자료를 `references/` 폴더에 복사한다.
3. `CURSOR_START_PROMPT.md` 전체를 Cursor Agent 대화에 입력한다.
4. 구현 중에는 프로젝트 루트 `AGENTS.md`와 `docs/TECH_SPEC.md`를 지침으로 참고하게 한다.
5. 처음에는 Mock 모드로 완성하고, Flow가 준비되면 API 연결을 별도 작업으로 진행한다.

**원본 HTML을 읽어 화면과 데이터를 확정했다. 변경된 업무 규칙은 `docs/HTML_ANALYSIS.md`에 적어 두었다.**
